Six roles, seven levels of access

Every cell in the matrix below is one of the seven levels defined here. The same seven levels apply uniformly across all thirteen modules — a module's card only needs to say where a role departs from the default.

Super Admin
Admin

FullCreate, edit, delete, and change module-wide settings.
ManageDay-to-day create/edit within the module — not its structural settings.
OwnManage rights, but only over records assigned to them (their batch, their session).
SubmitsCan create and submit, but it needs Admin/Super Admin approval before it counts.
ViewRead-only — sees the record, can't change it.
SelfSees and acts only on their own record — a student's own submissions, own timetable.

01 / 13
01 — Overview

Overview

Super Admin · Admin

The landing dashboard after login — a snapshot of the school right now, not a module you configure.

Key tiles
Active studentsActive batchesToday's classesPending enquiriesLesson plans awaiting reviewRecent activity feedQuick actions
Role notes

Admin sees the same dashboard minus the tiles tied to Super-Admin-only settings (design tokens, role creation). Teacher, Guest Faculty, Staff and Student don't get this module at all — each lands on a role-appropriate home screen instead (a teacher's own batch list, a student's own dashboard), which isn't part of the 13-module count.

Reads from: Users, Batches, Timetable, Enquiries, Lesson Plans — this module has no data of its own.
02 / 13
02 — Users

Users

Super Admin · Admin (limited)

The single source of truth for every account — nobody self-registers on the staff side.

Key fields
Name & contactRoleAssigned batches/disciplinesStatus (active/inactive)Public-profile togglePermission overrides
Workflow
Invite created→Account set up (temp password / invite link)→Profile completed→Public profile toggled if faculty
Role notes

Admin (Manage*) can create and edit Teacher, Guest Faculty, Staff and Student accounts, but cannot create or edit an Admin or Super Admin account — that boundary is what stops privilege escalation. Only Super Admin can create another Admin.

Feeds: the public Faculty Directory (Phase 2), and the assignment fields inside every other module.
03 / 13
03 — Curriculum

Curriculum

Super Admin · Admin · view for others

The structure of what's taught — disciplines, levels and the syllabus documents behind them.

Key fields
Discipline nameDescriptionLevels / gradesSyllabus documentsLearning outcomesUGC curriculum referencesLead faculty
Role notes

Guest Faculty (View*) sees only the discipline(s) they teach, not the full curriculum. Student (Self*) sees only the syllabus for the discipline they're enrolled in — this is their read of Curriculum, not a separate record.

Feeds: the public Courses page (Phase 2). Referenced by: Batches (a batch belongs to a discipline+level), Timetable.
04 / 13
04 — Timetable & Schedules

Timetable & Schedules

Super Admin · Admin

When and where every class happens, with conflicts caught before they become a problem.

Key fields
BatchFacultyDiscipline/subjectDay & timeRoom / online linkRecurrence rule
Workflow
Admin builds recurring schedule per batch→Conflicts flagged automatically→Published to affected faculty & students
Role notes

Teacher / Guest Faculty (View*) see only their own schedule, not the full school timetable. Student (Self) sees only their own batch's timetable.

Reads from: Batches, Users. Feeds: Live Classes (a session's join link is generated from its timetable entry).

05 — Batches

Batches

Super Admin · Admin

The cohort — who's enrolled, with whom, taught by whom.

Key fields
Batch nameDiscipline & levelAssigned facultyStudent rosterCapacityStart date
Role notes

Teacher / Guest Faculty (View*) see the roster only for the batch(es) they're assigned to.

Referenced by: Timetable, Lesson Plans, Live Classes, Assignments, Feedback and Activities — every one of those scopes to a batch.
06 / 13
06 — Lesson Plans

Lesson Plans

Teacher · Guest Faculty · approved by Admin

What will actually be taught, session by session — drafted by the person teaching it, checked by Admin before it's final.

Key fields
BatchSubjectSession dateObjectivesContent / methodMaterialsStatus: draft → submitted → approved / needs revision
Workflow
Teacher/Guest Faculty drafts→Submits for review→Admin approvesorsends back with comments
Role notes

Teacher / Guest Faculty (Own*) can create, edit and submit only for their own batches — this is a Submits-level right in practice, since nothing is final until Admin approves it. Templates from a previous term can be duplicated to save re-writing routine plans.

Scoped by: Batches, Curriculum. Can attach to: a Live Classes session as its agenda.
07 / 13
07 — Live Classes

Live Classes

Teacher · Guest Faculty · Student joins

Where class actually happens online — built around the free, embedded Jitsi Meet decision from Phase 1.

Key fields
Linked timetable sessionRoom linkStart / end timeRecording URLAttendance list
Workflow
Session scheduled in Timetable→Room link auto-generated→Teacher starts, students join→Attendance logged automatically→Recording archived
Role notes

Teacher / Guest Faculty (Own*) can only start or manage sessions for their own assigned batches. Student (Self, join) sees join links and recordings only for batches they're enrolled in.

Reads from: Timetable, Batches. Can spawn: an Assignment straight out of a session.
08 / 13
08 — Assignments

Assignments

Teacher · Guest Faculty · Student submits

Practice and evaluation between classes — including performance submissions, not just written work.

Key fields
BatchTitle & instructionsAttachmentDue dateSubmission type: file / text / audio-videoGrade / scoreFeedback text
Workflow
Teacher creates & assigns to batch→Students submit by due date→Teacher grades & returns feedback
Role notes

Audio/video submission matters here specifically — a Bharatanatyam or Mridangam assignment is often "record yourself and upload," not text. Teacher / Guest Faculty (Own*) only for their own batches. Student (Self, submit) sees and submits only their own.

Scoped by: Batches. Feeds: Feedback, and the Student's own dashboard.
09 / 13
09 — Feedback

Feedback

Teacher · Student · Admin analytics

A structured, two-way loop — not just a suggestion box.

Key fields
Type: student→faculty / faculty→student / peerCycle / periodForm questionsResponsesAggregate rating
Workflow
Admin or Teacher opens a cycle for a batch→Students respond (can be anonymous)→Results aggregate for Admin's analytics view
Role notes

Teacher / Guest Faculty (Own*) give and receive feedback only within their own batches. Student (Self) submits feedback and sees feedback given to them, not classmates' records.

Scoped by: Batches, Assignments (per-assignment feedback threads).
10 / 13
10 — Events

Events

Staff drafts · Admin publishes

Everything happening beyond regular classes, with a publish gate so nothing reaches the public site unreviewed.

Key fields
Title & descriptionDate / time / venueType: internal / publicRSVP listCover imagePublic-visibility toggle
Workflow
Staff drafts the event→Admin/Super Admin reviews & publishes→RSVPs collected→Attendance marked on the day
Role notes

Staff (Drafts*) can create and edit events and manage RSVPs, but the toggle that puts an event on the public Events page is reserved for Admin/Super Admin — the same draft-preview-publish discipline the CMS uses in Phase 1.

Feeds: the public Events page (Phase 2). Can feed: Activities, for performance events.
11 / 13
11 — Jobs

Jobs

Staff drafts · Admin publishes

Recruiting guest faculty and staff, with applicants tracked in one place instead of an inbox.

Key fields
Title & typeDescription & requirementsStatus: draft / published / closedApplicant stage: new → shortlisted → interview → offer → rejected
Workflow
Staff drafts posting→Admin/Super Admin publishes to Careers→Applications arrive→Staff/Admin move applicants through stages
Role notes

Same publish gate as Events: Staff (Drafts*) prepares the posting, Admin/Super Admin puts it live.

Feeds: the public Careers page (Phase 2). On hire: creates the new Guest Faculty/Staff account in Users.
12 / 13
12 — Enquiries

Enquiries

Staff · Admin

Every admissions or general enquiry from the public site, caught in one inbox instead of scattered across email.

Key fields
Name & contactType: Admission / GeneralMessageDiscipline of interestStatus: new → contacted → converted / closedAssigned staffNotes / history
Workflow
Enquiry submitted on public site→Lands as "new"→Staff/Admin assigns & contacts→Status updates through to converted or closed
Role notes

"Converted" is the one status with a side effect worth designing for now: it can auto-create the Student record in Users, so admissions staff aren't re-typing what the enquiry already captured.

Fed by: the Admissions and Contact forms (Phase 2). Creates: Student accounts in Users, on conversion.

13 — Activities

Activities

Staff · Teacher · Student views own

The co-curricular record — competitions, performances, achievements — that a certificate or portfolio can eventually draw on.

Key fields
Student(s) / batchActivity typeDateDescriptionResult / achievementEvidence: photo / certificate
Workflow
Staff/Teacher logs the activity→Participating students tagged→Appears on each student's own record
Role notes

Teacher / Guest Faculty (Own*) log activities only for their own batch. Student (Self, view) sees only their own activity history.

Scoped by: Batches, Users. Can feed: the public Gallery & News page (Phase 2), when a photo from a logged activity is reused there.
