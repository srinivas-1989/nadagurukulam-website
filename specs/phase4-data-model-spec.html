01 — The two-database split

Structured and permissioned vs. flexible and content-shaped

This is the Phase 1 architecture decision, made concrete: anything relational — it has a fixed shape, gets queried by joins, and carries row-level permissions — goes in Supabase. Anything whose shape varies record to record, or that's closer to a document than a row, goes in MongoDB.

02 — The hybrid-record rule

One recurring pattern, so the split doesn't fight itself

A few things in Phase 3 (Curriculum, most visibly) don't cleanly belong to one database — a discipline has structured fields you'd want to query and permission (name, level, lead faculty) and a long, richly-formatted body (the actual syllabus) that behaves like content. Rather than force one or the other, one rule applies everywhere this comes up:

The hybrid-record rule:

The structured, queryable, permissioned part of a record always lives in Postgres as its own row. If that record also has a flexible, richly-formatted body, that body lives in MongoDB as its own document, and the Postgres row holds a single reference column pointing to it (e.g. disciplines.syllabus_content_id). The app reads both and joins them at the API layer — Postgres is never queried for the body text, and Mongo never has to enforce a permission it doesn't understand.

This is why disciplines appears in Postgres below with a syllabus_content_id column, while the syllabus text itself is a curriculum_content document in Mongo.

05
05 — Documents & sensitive data

From "Supabase now, cheaper later" to an actual schema

Phase 1 resolved the direction: Supabase Storage holds files today, with Cloudflare R2 or Backblaze B2 as the cost-efficient move once the library grows, plus an encrypted offline backup for the most sensitive records. The documents and document_access_log tables above are what make that real.

1

Every file is a row, not a loose object

Nothing is ever linked to directly by URL. A visitor or teacher hits the API, which checks documents.visibility against their role, then issues a short-lived signed URL — so moving the actual bytes from Supabase Storage to R2/B2 later never breaks a link anyone has bookmarked.

2

Visibility is a value, not a folder

documents.visibility holds one of: public (UGC/Compliance page), students, staff, or a specific role list — checked on every read, so a document's audience can change without moving the file.

3

is_sensitive triggers the extra handling

ID proof, medical notes, anything involving minors gets is_sensitive = true: encrypted at rest, included in the periodic encrypted offline backup, and every view/download is written to document_access_log — not just permitted, but recorded.

4

The access log is append-only

document_access_log is written to, never edited or deleted by the application — it's the record you'd need if you ever had to answer "who saw this."

06 — Enforcing the Phase 3 permission matrix

Where the matrix actually lives in code

The matrix from Phase 3 isn't just documentation — each cell becomes an enforced rule at exactly one of two layers, depending on which database the data sits in.

Postgres tables → Row-Level Security policies. Supabase's RLS runs the check inside the database itself: a policy on batches literally says "a Teacher may select this row only if their user_id appears in batch_faculty for this batch_id" — which is the database-level version of Phase 3's "Own*" cells. Even a bug in application code can't leak another teacher's batch, because the database refuses the query itself.
MongoDB collections → checked in the API layer. Mongo has no equivalent to RLS, so every read/write to lesson_plans, feedback_responses, activities and the rest passes through the Render backend, which re-derives the same "Own scope" and "Self" rules from the requester's role and their rows in Postgres (their batch_faculty or enrollments entries) before it will return a document.
